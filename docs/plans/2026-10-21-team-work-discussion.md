# 双人任务先讨论后工作

## 目标

双人任务真正被两位居民领取后，系统安排两人集合到同一地点，进入任务专属 Conversation。两人交流并确认协作模式和职责，讨论结束后才开放代码操作。沿用现有 Move、Rest、Conversation 和 Work，不新增邀约审批流程或职责对应的文件权限。

## 状态与流程

以 TASK_CLAIMED 对应的领取实例为单位保存一份任务协作记录：两位成员、集合地点、讨论会话、当前提案和 relay 写入者。领取申请和组队邀请不触发讨论，单人任务保持原行为。记录随 Activity 状态保存，领取失效或重新领取后不能沿用旧协议。

领取成功后，在安全边界安排集合：正在运行的工具和已经开始的发言先结束，移动中的居民先到达，再按真实路径前往公共工作地点。先到者可以等待。跨日或地点关闭时保留未完成义务；普通离开不会被每个调度 tick 立即拉回，但再次尝试 Work 或次日会恢复安排。

讨论使用两个简短工具：propose_work_plan 提出 parallel 或 relay、双方职责，以及 relay 的首位写入者；confirm_work_plan 由搭档确认当前提案。提案人默认同意自己的提案，不允许自我确认或确认已被替换的提案。确认前双方都须有真实送达的非空发言。提案更新通知搭档并唤醒该讨论中的 Wait。任务讨论暂不采用普通聊天的发言后自动 Wait，使居民可以接着提案或确认。

确认方案后收尾讨论，等待已经开始的发言结束。只有协议确认且会话真正结束，代码读取、修改、测试、提交和交接才开放。工具菜单与执行入口共同遵守此条件，进入其他 Work 不能绕过。

## 协作模式

Work 不再各自选择模式，而是读取同一份任务协议。parallel 继续使用个人工作区和显式补丁交接；relay 的首位写入者由协议决定，现有交接过程更新任务级写入者。职责是双方可见的协作说明，不限制文件或任务 part 的操作权限。

## 验证与发布

验证直接组队和自动配对各自只生成一场讨论、双方发言与确认、旧提案拒绝、异地移动和已有行动收尾、离开及跨日恢复、不同 Work 的共享权限，以及 relay 交接。运行本地和 Linux 回归及前端检查，再提交推送并更新 Zenith 默认版本。当前冻结运行的实验保持原版本，不自动新开实验。
